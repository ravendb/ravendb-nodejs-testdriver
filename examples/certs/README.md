# Test certificates

Self-signed certificates for the secured-server example (scenario 07 in each
runner folder). Generated by [generate.sh](generate.sh).

| File | What it is |
| --- | --- |
| `ca.crt` | The CA that signed the certificate below. The client is told to trust it, since nothing else will. |
| `server.pfx` | Certificate + private key, no password. RavenDB loads this, and the driver's document stores authenticate with the same file. |
| `server.crt` | The same certificate without the key, so the example can read its thumbprint — node's `X509Certificate` parses PEM and DER, but not PKCS#12. |

One certificate covers both roles, which is what `ServerOptions.secured()`
expects: the server presents it, the client authenticates with it, and its
thumbprint is registered as `--Security.WellKnownCertificates.Admin`
automatically. It carries both `serverAuth` and `clientAuth` extended key usages
for that reason, and is issued for `localhost` / `127.0.0.1` / `::1` — the name
the server binds to must be covered by the certificate's SAN or the TLS
handshake fails.

## These keys are public on purpose

The private key in `server.pfx` is committed to this repository. That is
deliberate: it protects a throwaway RavenDB server that runs on localhost for a
few seconds during an example test run, and nothing else. Secret scanners may
flag it.

Do not reuse these certificates for anything. Do not copy this arrangement into
a real deployment.

## Regenerating

```bash
./generate.sh
```

Needs `openssl` on `PATH`. The certificates are valid for 10 years; regenerate
when they expire. The examples read the thumbprint at runtime, so no code change
is needed afterwards.
